# Releasing

Releases are driven by [Changesets](https://changesets.dev) and published to npm and
crates.io with trusted publishing — OIDC on both registries, no long-lived token in
the repo.

## The everyday loop

1. Every PR that changes something publishable includes a changeset:

   ```sh
   bun run change
   ```

   That writes a markdown file into `.changeset/`. Commit it with the PR.

2. Merging to `main` runs `.github/workflows/release.yml`. `select-mode` sees
   pending changesets and opens (or refreshes) a **Version Packages** PR that
   bumps versions and writes CHANGELOGs. It is generated by the root `version`
   script, so the PR also carries the crates' version bump and both `Cargo.lock`
   files — see [Crates](#crates).

3. Merging the Version Packages PR leaves no changesets behind. The next run of
   the workflow flips to publish mode: it builds both addons on all six targets,
   publishes the npm packages, then the crates, then checks the registry items
   against what npm now has (`check:registry --published`).

`@build-qube/papyra`, `@build-qube/papyra-native`, `@build-qube/papyra-office-native`,
`@build-qube/papyra-pdfjs` and `@build-qube/papyra-tauri` are in `fixed` in
`.changeset/config.json`, so they always release together on the same version, and
the crates take that version too. `papyra-demo`, `papyra-bench` and `@workspace/ui`
are in `ignore` and never publish.

## What actually gets published

Seventeen npm packages and four crates. napi-rs splits each addon's binary out into
one package per platform, and the loader in its `index.js` picks the right one at
runtime.

| Package | Published by |
| --- | --- |
| `@build-qube/papyra` | `changeset publish` |
| `@build-qube/papyra-pdfjs` | `changeset publish` |
| `@build-qube/papyra-tauri` | `changeset publish` |
| `@build-qube/papyra-native` | `changeset publish` |
| `@build-qube/papyra-native-{darwin-arm64,darwin-x64,linux-x64-gnu,linux-arm64-gnu,win32-x64-msvc,wasm32-wasi}` | `napi prepublish` |
| `@build-qube/papyra-office-native` | `changeset publish` |
| `@build-qube/papyra-office-native-{darwin-arm64,darwin-x64,linux-x64-gnu,linux-arm64-gnu,win32-x64-msvc,wasm32-wasi}` | `napi prepublish` |
| crates `papyra-core`, `papyra-encode`, `papyra-hayro`, `papyra-tables`, `papyra-tiff`, `tauri-plugin-papyra` | the `crates` job |

The platform packages are generated at release time from the `napi.targets` list
in each addon's `package.json`, filled with the CI build artifacts, and published by
the `publish-platforms` step of the root `release` script, which runs before
`changeset publish`. **Adding a target to `napi.targets` adds a package per
addon**, and each needs bootstrapping before it can go out — see
[New package names](#new-package-names).

`release` also builds the three TypeScript packages first. They ship `files:
["dist"]` and have no `prepack` hook, so a package left out of that build publishes
without its `dist`.

The platform step deliberately does *not* live in a `prepublishOnly` hook.
`changeset publish` shells out to `npm publish --json`, and npm collapses a
lifecycle script's entire stderr into a single `"command failed"` string — a
registry rejection inside the hook is undiagnosable from the workflow log. Running
it as its own step keeps the real error visible.

## Crates

The crates follow npm: there is no Cargo-side changeset. The root `version` script
is `changeset version && bun run scripts/sync-crate-versions.ts`, and the script
copies `@build-qube/papyra`'s new version into:

- `[workspace.package] version` in the root `Cargo.toml` — every root crate inherits
  it, published or not;
- the `version` beside `path` on `papyra-core`, `papyra-encode`, `papyra-hayro`,
  `papyra-tables` and `papyra-tiff`, in the root `[workspace.dependencies]` and in
  `crates/tauri-plugin-papyra`, which is its own Cargo workspace;
- the plugin's own `version`, and the unpublished office plugin's beside it, which
  apps take from git at the same tag;
- both `Cargo.lock` files, through `cargo update -w`, which moves only the
  workspaces' own packages.

The version job passes that script to `changesets/action/version` as `script`, which
is why the bump lands in the Version Packages PR rather than on a commit nobody
reviewed.

The `crates` job runs after the npm publish, on macOS (`cargo publish` verifies by
compiling, and Tauri on Linux needs webkit2gtk's headers). It exchanges its OIDC
token for a 30-minute crates.io token with `rust-lang/crates-io-auth-action`, then
publishes in dependency order: core, encode, hayro, tables, tiff, plugin.
`tauri-plugin-papyra-office` is `publish = false` and never goes out: its engines
are git dependencies, which crates.io refuses. A crate whose version is
already in the index is skipped, so **re-running the failed job** finishes a partial
release. A fresh push would not: once npm has the version, `select-mode` no longer
picks publish mode.

To dry-run locally: `cargo publish --dry-run -p papyra-core -p papyra-encode -p
papyra-hayro -p papyra-tables -p papyra-tiff` from the root verifies the five
against each other. The plugin needs
its dependencies at the new version on crates.io, which before a release they are
not; point it at the local copies instead:

```sh
cd crates/tauri-plugin-papyra
cargo publish --dry-run \
  --config 'patch.crates-io.papyra-core.path="../papyra-core"' \
  --config 'patch.crates-io.papyra-encode.path="../papyra-encode"' \
  --config 'patch.crates-io.papyra-hayro.path="../papyra-hayro"' \
  --config 'patch.crates-io.papyra-tables.path="../papyra-tables"' \
  --config 'patch.crates-io.papyra-tiff.path="../papyra-tiff"' \
  -p tauri-plugin-papyra --all-features
```

## New package names

Neither registry lets you attach a trusted publisher to a name that does not exist
yet ([npm/cli#8544](https://github.com/npm/cli/issues/8544)), so a new package is
bootstrapped by hand once: create the name with a placeholder, then trust
`release.yml`. That is how the 0.5.0 names were done — the nine npm packages
(`papyra-pdfjs`, `papyra-tauri`, `papyra-office-native` and its six platform
packages) and the four crates. Nothing here is needed again until a new name is.

### npm

1. Publish a placeholder, off `latest`'s path as far as npm allows:

   ```sh
   npm publish --tag bootstrap --access public   # version 0.0.0-bootstrap.0
   ```

   A brand-new name shows a `0.0.0-stage` stub and takes about seven minutes to
   become visible; `npm view` misses it until then. npm also points `latest` at
   the first version a package has, so `latest` is the placeholder until the real
   release replaces it.
2. Trust the workflow. This needs **npm 12 or later** — npm 11 lists the flags in
   `npm trust --help` but its `github` subcommand rejects them, and without a
   permission the registry answers with a bare 400:

   ```sh
   npm trust github <pkg> --repo BuildQube/Papyra --file release.yml \
     --allow-publish --allow-stage-publish -y
   ```

   or, on npmjs.com, **Package → Settings → Trusted Publisher → GitHub Actions**
   with `BuildQube` / `Papyra` / `release.yml` and no environment.

Every npm call against the account needs browser 2FA, `npm trust list` included.
Approve once and tick "skip 2FA for 5 minutes", and do not capture npm's stdout in a
script, or the prompt cannot show and the call fails with `EOTP`.

The workflow filename must be exactly `release.yml`. This is why publishing lives
in its own workflow and why the build matrix is duplicated there rather than
pulled in with `workflow_call` — npm validates the OIDC claim against the workflow
that contains the publish step, and a reusable workflow reports the *caller's*
filename instead, which fails the check. Every package needs it, platform packages
included: napi publishes those with its own `npm publish` calls, and npm checks the
claim per package.

### crates.io

1. Publish a `0.0.0` placeholder with a personal token (`cargo publish`); the account
   needs a verified email.
2. On crates.io, **Crate → Settings → Trusted Publishing → Add**: `BuildQube` /
   `Papyra` / `release.yml`, no environment. `GET
   /api/v1/trusted_publishing/github_configs?crate=<name>`, with the token as
   `Authorization`, confirms it.
3. Add the crate to the loop in the `crates` job, in dependency order, and to
   `scripts/sync-crate-versions.ts` if it is depended on by path.

## After the first release of a new name

Once a release has gone out over OIDC — the placeholders and tokens are the way
back until then:

- [ ] `npm deprecate <pkg>@0.0.0-bootstrap.0 "placeholder; use a real release"` for
      each bootstrapped package.
- [ ] `npm dist-tag rm <pkg> bootstrap` for each.
- [ ] npm, each package: **Settings → Publishing access → Require two-factor
      authentication and disallow tokens**. This is what actually buys something:
      after it, a stolen token cannot publish papyra at all.
- [ ] crates.io, each crate: **Settings → Trusted Publishing → trusted publishing
      only**.
- [ ] Delete the `NPM_TOKEN` repository secret (`gh secret delete NPM_TOKEN --repo
      BuildQube/Papyra`). Nothing reads it.
- [ ] Revoke the crates.io token used for the placeholders.

For 0.5.0 that is the nine npm packages and the four crates listed above.

npm and crates.io need no `--provenance` flag: both attach provenance to a trusted
publish on their own.

## Requirements the workflow already handles

- **`id-token: write`** — only on the `publish` and `crates` jobs. Nothing else in
  this repo requests it, which is also why `check:registry --published` is a job of
  its own rather than a step after Publish.
- **npm >= 11.5.1** — OIDC support landed there. The publish job runs
  `npm install -g npm@latest` rather than trusting the runner image.
- **`registry-url` on `setup-node`** — needed even without a token; without it npm
  does not attempt the OIDC exchange.
- **npm, not bun** — `changeset publish` shells out to `npm publish` (changesets
  falls back to npm for any package manager it does not special-case), and so does
  `napi prepublish`. `bun publish` has no OIDC support, so this matters.

One repo setting is *not* in the workflow: **Settings → Actions → General →
Allow GitHub Actions to create and approve pull requests** must be enabled, or the
Version Packages PR cannot be opened.

## Troubleshooting

**`E404 Not Found - PUT https://registry.npmjs.org/@build-qube%2f...`** during an
OIDC publish usually means that specific package has no trusted publisher
configured — the scoped-package case is a
[known sharp edge](https://github.com/npm/cli/issues/8976). Check all seventeen,
platform packages included.

**`npm whoami` succeeds but publishing is rejected.** Authentication and
authorisation are different questions: a granular token with org access but no
**Packages and scopes** permission authenticates fine and cannot publish a thing.
Check that section of the token page, not just that the token works.

**The publish job fails with nothing but `command failed`.** That is npm folding a
lifecycle script's stderr into one string. If you see it, something has been moved
back into a `prepublishOnly`/`prepack` hook — run it as its own step in the
`release` script instead, where the real error prints.

**A published package fails to install with `EUNSUPPORTEDPROTOCOL`.** Something
in a publishable manifest uses a `workspace:` range. Changesets publishes through
`npm publish`, and unlike pnpm/yarn/bun, npm does not rewrite that protocol while
packing — it goes to the registry verbatim and no consumer can install it.
`bun run check:publishable` guards against this in CI and again in the `release`
script; depend on the real version instead and let Changesets keep it in step.

**A platform package is missing from a release.** `napi prepublish` only publishes
what it finds under `npm/<platform>/` in the addon's package, which is filled from the
CI artifacts. If a build matrix leg failed, its package is silently skipped —
check the `build` jobs before assuming the publish worked.

**The `registry` job fails right after a publish.** npm can take a minute to serve a
new version everywhere, and `check:registry --published` installs the release it
just made. If the failure is an unresolvable `@build-qube/papyra@^x`, re-run the job;
it publishes nothing.

**The Version Packages PR does not appear.** Either the "allow Actions to create
pull requests" setting above is off, or there were no changesets to version.
